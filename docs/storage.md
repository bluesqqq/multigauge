# Multigauge Storage Layout

This document is the source of truth for package upload, installed storage, and the package-manager API.

The core assumes one configurable data root:

```text
<dataRoot>/
  library.json
  state.json
  packages/
    <package-id>/
      manifest.json
      faces/
        <face-id>.json
```

## Data Root

`<dataRoot>` is the base directory chosen by the platform implementation.

Examples:

- ESP32: `/multigauge`
- Linux: a user data directory such as `~/.local/share/multigauge`

All internal paths are resolved relative to this root.

## Package Contract

Uploaded packages use one unified object schema only.

Raw face-array uploads are rejected.

The uploaded and exported package document contains only user-facing/package data:

- `name`
- `author`
- `description`
- `faces`

It must not contain:

- internal package ids
- internal face ids
- filesystem paths
- runtime-only fields

The schema lives in [`docs/schemas/package.schema.json`](./schemas/package.schema.json).

Each face entry contains:

- `name`
- `face`

`face` is the opaque gauge-face payload loaded by `GaugeFace`.

## `library.json`

`library.json` is the fast package browsing index used by the UI.

It contains package-level lookup data only:

- `id`
- `name`
- `author`

`id` is the internal package id. It exists in `library.json` and the package directory name, not in `manifest.json`.

`name` is the display name used by the UI. If multiple installed packages share the same imported name, the library entry may be suffixed so the UI can keep them distinct.

`library.json` is regenerated by scanning installed package manifests, so it stays derived from the installed package set rather than acting as the source of truth.

The schema lives in [`docs/schemas/library.schema.json`](./schemas/library.schema.json).

## `state.json`

`state.json` stores persisted user/runtime state.

It is separate from package import/export data.

## `packages/`

`packages/` contains all installed gauge packages.

Each package has its own directory keyed by the generated internal package id.

### `manifest.json`

`manifest.json` is the internal installed-package record.

It stores:

- package metadata
- the installed face list as internal face id + user-facing face name

It does not store:

- the package id
- filesystem paths
- asset listings

It also does not store any face payloads. The manifest only keeps the face ids, face names, and package-level metadata needed to rebuild the original package document later.

The schema lives in [`docs/schemas/manifest.schema.json`](./schemas/manifest.schema.json).

Current manifest fields:

- `name`
- `author`
- `description`
- `faces`

Each face entry contains:

- `id`
- `name`

`id` is the generated internal face id. It is derived from the face name by lowercasing and replacing spaces or punctuation with hyphens. If an id already exists within the package, a numeric suffix is added.

The face payload itself is stored separately at the derived path:

- `faces/<face-id>.json`

### `faces/`

`faces/` contains the stored gauge face JSON files for the package.

Each face is stored as a separate JSON file.

The file name is derived from the face id. For example, a face with id `main-cluster` is stored at:

- `faces/main-cluster.json`

There is no stored path field in the manifest.

## Package Manager API

### `listPackages()`

Returns the parsed `library.json` document.

The returned shape is:

```json
{
  "packages": [
    { "id": "...", "name": "...", "author": "..." }
  ]
}
```

### `listFaces(packageId)`

Returns the face list for an installed package from the package-manager cache.

The cache is populated from installed manifests during import and `rebuildLibrary()`, so the web UI does not need to parse manifests on the request thread.

The returned shape is:

```json
{
  "faces": [
    { "id": "...", "name": "..." }
  ]
}
```

### `getFace(packageId, faceId)`

Reads and returns the stored face JSON from:

- `packages/<package-id>/faces/<face-id>.json`

The path is derived internally from the package id and face id.

### `getPackage(packageId)`

Returns `packages/<package-id>/manifest.json` exactly as stored.

### `exportPackage(packageId)`

Reconstructs the original imported package document exactly:

- same package-level fields
- same face order
- same user-facing face names
- no internal ids
- no paths

The export is rebuilt from the manifest plus the stored face payloads.

## Import and Export Behavior

When a package is imported:

1. The package document is validated against the unified object schema.
2. The package manager generates a unique internal package id from the imported package name.
3. If a package with the same name already exists, the generated id and the library display name are suffixed so the installed packages remain distinct.
4. Each face is assigned a unique internal face id within that package.
5. Each face payload is written to `faces/<face-id>.json`.
6. `manifest.json` is written without a package id, path fields, or face payloads.
7. `library.json` is updated as the fast browsing index.
8. The package-manager face cache is updated from the just-imported face list.

When a package is exported:

1. The package manager reads the stored manifest.
2. The package manager reads each stored face payload using the derived face ids.
3. The exported document is reconstructed with the original face order and user-facing names.
4. The exported document does not include internal ids or paths.

## Web Upload And UI Safety Rules

The web server must follow these rules:

- accept only the unified object schema
- reject raw face arrays
- reject unsupported or malformed package shapes with consistent errors
- validate JSON before writing anything to storage
- derive all filesystem paths internally
- never trust client-provided ids, paths, or filenames as storage locations
- never expose arbitrary filesystem reads through the package UI
- use `listPackages()` for package browsing
- use `listFaces(packageId)` for face browsing
- show gauges only through the safe `packageId + faceId` loading path

The "Show gauge" menu should group faces under their installed package names.

## Source Of Truth

The authoritative installed-package data is:

- `packages/<package-id>/manifest.json`
- `packages/<package-id>/faces/<face-id>.json`
- `state.json` for user/runtime state

`library.json` is derived browsing data and may be regenerated.

Normal imports and removals update `library.json` incrementally from the package metadata that was just written or removed.

`rebuildLibrary()` performs a full rescan of installed package manifests, refreshes the face cache, and regenerates `library.json` from the installed package set.
